# Prompt: Sistema de Controle Financeiro Pessoal

## Como usar este prompt

Este documento é o **prompt de especificação de domínio**. Ele deve ser usado em conjunto com o prompt guard já existente (`01.md`), que define as regras de código (stack, shadcn/ui obrigatório, componentes em `@data`, Context7, cores do tema, unidades em `rem`, etc). Este prompt aqui **não repete** essas regras — ele define **o que** o sistema precisa fazer; o guard define **como** o código deve ser escrito.

## Contexto

Sistema pessoal de controle financeiro, multiusuário, onde cada usuário registra receitas e despesas e acompanha resumos gráficos mensais e por categoria. Baseado numa planilha de controle já em uso (anexa como referência), que deve servir de fonte da verdade para a estrutura de dados e categorias padrão.

## Stack

Definida no prompt guard (`01.md`): Next.js + React 19, API interna via Route Handlers do Next.js (sem backend separado), Prisma 7, shadcn/ui, npm.

## Autenticação

- Tela de login com e-mail e senha.
- Tela de cadastro de novo usuário.
- Sessão autenticada obrigatória para todas as rotas, exceto login/cadastro.
- Senha armazenada com hash (bcrypt), nunca em texto puro.
- **Todo dado é isolado por usuário** — um usuário nunca vê ou edita lançamentos, categorias ou formas de pagamento de outro usuário. Toda query no `@data` deve filtrar pelo `usuarioId` da sessão atual.

## Correção em relação à descrição original

O requisito original listava "Tipo (Salário e Alimentação já inseridos)" — isso na verdade corresponde à **Categoria**, não ao Tipo. Baseado na planilha de referência, o modelo correto é:

- **Tipo**: classificação macro, com apenas dois valores fixos — `Receita` ou `Despesa`.
- **Categoria**: classificação detalhada, vinculada a um Tipo (uma categoria é sempre de receita OU de despesa, nunca as duas). Isso faz o formulário filtrar automaticamv ente as categorias certas conforme o Tipo escolhido.

## Modelagem do banco (Prisma)

> Observação sobre **Mês**: na planilha ele é uma coluna auxiliar calculada a partir da Data. Não recomendo uma tabela própria pra isso — o mês é extraído da `data` do lançamento em tempo de consulta (`MONTH(data)` / agrupamento por mês). Se no futuro for necessário permitir nomes de mês customizados ou tradução, aí sim vale uma tabela de apoio — mas para o escopo atual isso seria complexidade desnecessária.

```prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql" // ou "sqlite" para desenvolvimento local
  url      = env("DATABASE_URL")
}

model Usuario {
  id        String   @id @default(cuid())
  nome      String?
  email     String   @unique
  senha     String
  criadoEm  DateTime @default(now())

  categorias      Categoria[]
  formasPagamento FormaPagamento[]
  lancamentos     Lancamento[]
}

enum TipoLancamento {
  RECEITA
  DESPESA
}

model Categoria {
  id        String         @id @default(cuid())
  nome      String
  tipo      TipoLancamento
  usuarioId String
  usuario   Usuario        @relation(fields: [usuarioId], references: [id])
  lancamentos Lancamento[]

  @@unique([usuarioId, nome, tipo])
}

model FormaPagamento {
  id        String   @id @default(cuid())
  nome      String
  usuarioId String
  usuario   Usuario  @relation(fields: [usuarioId], references: [id])
  lancamentos Lancamento[]

  @@unique([usuarioId, nome])
}

model Lancamento {
  id               String         @id @default(cuid())
  usuarioId        String
  usuario          Usuario        @relation(fields: [usuarioId], references: [id])
  data             DateTime
  tipo             TipoLancamento
  categoriaId      String
  categoria        Categoria      @relation(fields: [categoriaId], references: [id])
  descricao        String
  formaPagamentoId String
  formaPagamento   FormaPagamento @relation(fields: [formaPagamentoId], references: [id])
  valor            Decimal        @db.Decimal(10, 2)
  criadoEm         DateTime       @default(now())

  @@index([usuarioId, data])
}
```

### Por que Categoria e Forma de Pagamento são tabelas por usuário (não globais)

O requisito pede que o usuário possa criar/editar/remover categorias e formas de pagamento livremente. Se fossem tabelas globais compartilhadas, a edição de um usuário afetaria todos os outros. Por isso cada uma tem `usuarioId` e é seedada individualmente na criação da conta (ver seed abaixo) — o usuário edita livremente sem impactar ninguém.

### Seed de dados padrão (por novo usuário)

Ao criar a conta, popular automaticamente:

**Tipo Receita**: Salário, Diárias, Gratificações, Renda extra, Outros

**Tipo Despesa**: Aluguel/Financiamento, Condomínio, Água, Energia, Internet/Telefone, Plano de saúde, Seguros, Mensalidades, Alimentação, Supermercado, Combustível, Restaurantes, Lazer, Viagens

**Formas de pagamento**: Depósito, PIX (e o usuário adiciona outras como cartão, dinheiro, etc — mencionadas nas instruções da planilha original)

## Estrutura de telas

### 1. Login / Cadastro
Formulários simples com validação, usando componentes shadcn (`Form`, `Input`, `Button`, `Card`).

### 2. Dashboard (tela principal após login)
- Resumo do mês atual: total de receitas, total de despesas, saldo.
- Gráfico de pizza — **resumo por categoria** do mês selecionado (usando cores do tema, vivas e distintas por fatia).
- Gráfico de pizza — **resumo mensal** (receitas vs. despesas do mês, ou distribuição dos últimos meses — usar criatividade conforme o guard já autoriza).
- Filtro de mês/ano para os gráficos.

### 3. Lançamentos (CRUD principal)
- Formulário de novo lançamento: Data, Tipo (Receita/Despesa — ao selecionar, filtra o dropdown de Categoria), Categoria, Descrição, Forma de Pagamento, Valor.
- Tabela/lista de lançamentos existentes, com edição e exclusão.
- Filtros por mês, tipo e categoria.

### 4. Gerenciar Categorias
- CRUD de categorias do usuário, sempre associadas a um Tipo (Receita ou Despesa).

### 5. Gerenciar Formas de Pagamento
- CRUD simples de formas de pagamento do usuário.

## Requisitos funcionais adicionais

- Toda mutação (criar/editar/excluir lançamento, categoria, forma de pagamento) passa por uma função em `@data`, nunca chamando o Prisma direto do componente (regra já definida no guard, reforçando aqui por ser crítico para a integridade multiusuário).
- Validação de que uma `Categoria` selecionada no formulário de lançamento pertence ao mesmo `usuarioId` da sessão E ao mesmo `Tipo` selecionado — evita inconsistência entre Tipo e Categoria.
- Ao excluir uma Categoria ou Forma de Pagamento que já tem lançamentos vinculados, decidir entre bloquear a exclusão (recomendado, para não perder histórico) ou pedir confirmação explícita informando quantos lançamentos serão afetados.
- Valores monetários em `Decimal`, nunca `Float`, para evitar erro de arredondamento — formatados em Real (R$) na exibição.
- Gráficos: usar biblioteca compatível com shadcn/ui (ex: `recharts`, que é a base dos componentes de gráfico do próprio shadcn) em vez de introduzir uma lib de gráficos concorrente.

## Entregáveis esperados

1. Schema Prisma completo conforme especificado.
2. Script de seed com as categorias e formas de pagamento padrão por novo usuário.
3. Rotas de autenticação (login, cadastro, logout) e proteção de sessão.
4. Funções de acesso a dados em `@data` para todas as entidades (Usuario, Categoria, FormaPagamento, Lancamento), sempre filtrando por usuário autenticado.
5. Telas: Login/Cadastro, Dashboard com os dois gráficos de pizza, CRUD de Lançamentos, CRUD de Categorias, CRUD de Formas de Pagamento.
